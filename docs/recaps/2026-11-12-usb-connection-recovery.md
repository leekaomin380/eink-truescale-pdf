# USB 黄色连接状态：原因、修复与验证

2026-11-12，已安装到本机并重启生效；后续用户授权同步源码和官网日志，不创建新的二进制发行版。

## 现场证据与原因边界

- 初始 IORegistry：Fujitsu FMVDP51，产品 ID 5718（0x1656），存在串口和 MTP 接口，未建立 en5 网络接口。
- 原安装应用 PID 1707 持续运行，显示黄色。执行应用自带 `check` 后，同一线材变为产品 ID 5719（0x1657），en5 active；认证和目录读取成功，根目录 11 项。
- 因而可以确认此次停在 USB 模式初始化阶段，同一线材可以完成数据通信。不能凭一次成功排除线材的所有间歇性故障。
- 原监视器按串口路径缓存“已切换”，成功条件仅是写入 10 字节且 drain 线程结束，未确认设备变成网络模式，也未检查 `tcdrain` 返回值。
- 同一串口即使命令未生效也不再重试；清缓存依赖某次轮询同时看到无设备且无串口。快速重插、设备重新枚举、设备仍挂在 USB 上时退回串口，都可能漏掉这一条件。
- 另有一条永久失效路径：Swift drain 线程若永不返回，全局 pending 标志会永久占用；后续切换继续失败。Python 投递路径原来也使用无期限 `tcdrain`。
- 监视器仅处理串口，投递工具还处理 network idle / carrier down，两套实现导致自动恢复能力不一致。Bonjour 浏览器失败后原来没有重建路径。
- 缺少故障发生前的切换日志，无法确认这次究竟由命令未生效、串口路径复用还是 drain 故障触发。以上是源码中可验证、通过故障场景测试覆盖的失效机制，不把假设写成现场已证事实。

## 统一的恢复规则

1. 按 IORegistry entry ID 区分设备枚举实例，不按可复用的 `/dev/cu.*` 名称记成功。
2. 根据当前 USB 网络模式、链路和服务发现判断状态；发送命令不等于连接成功。
3. 首次观察到设备留 3 秒正常初始化时间；恢复结束后按 3/6/12/24/30 秒退避。未观察到就绪就继续重试，同一时刻最多一个恢复任务。
4. 状态监视调用与投递相同的 `prepare_usb` 路径，覆盖串口切换与 USB 网络失效恢复。移除 Swift 中独立的串口发送和 drain 线程实现。
5. 后台恢复不排队占用前台投递：应用内共享队列忙则跳过；跨进程锁忙也立即退出。实际恢复进程限时 45 秒，超时终止后释放队列。
6. 串口发送处理部分写入、临时忙与中断；通过 `TIOCOUTQ` 在 2 秒期限内确认输出队列排空，避免无限 drain。
7. 重置硬件前重新读取当前链路，防止用先前的 idle 快照重置已自行恢复的链路。健康链路不会因服务发现迟到而被强制重置。
8. Bonjour 浏览器进入终止性失败后清除过时服务结果，30 秒后重建。USB 与 Wi-Fi 状态标签按实际 USB 链路区分。
9. 后台恢复记录观察到的枚举实例、产品模式、链路，以及准备操作结果/错误类型/errno，写入有大小上限的 `~/Library/Application Support/Quaderno Converter/Direct/usb-recovery.log`。未读取配对密钥。
