## 0. 关于本文档的写作时机

本文档**刻意不在项目启动时撰写，而是在完成一轮完整技术探索之后回写**。

原因：项目启动时对目标设备的关键事实一无所知，盲写的需求会把错误假设固化。
例如启动时最自然的写法是「支持 A4 与 A5 两种纸张尺寸」——
而事实上 **A4/A5 是富士通的产品型号名，与 ISO 纸张规格无关**，
两款设备的显示区宽高比均为 3:4（0.7500），而非 ISO 纸张的 0.707。
这一条若写进需求，会一路误导实现。

因此本文档的每一条需求，都尽量标注其**依据等级**：

| 标记 | 含义 |
|---|---|
| **【实测】** | 在真实设备上验证过 |
| **【推算】** | 由实测数据计算所得，逻辑可复核 |
| **【推论】** | 由机制推导，**尚未验证** |
| **【待定】** | 尚无依据，需决策或实验 |

## 1. 问题陈述

### 1.1 表层问题

将一段文本或一本电子书送到电子墨水设备上阅读，当前路径充满摩擦：

- **文本**：复制 → 打开笔记软件 → 粘贴 → Cmd+P → 在打印下拉菜单中寻找目标 → 确认
- **电子书**：设备只接受 PDF，而多数藏书是 EPUB；转换后「效果很差」

### 1.2 深层问题（本项目的核心发现）

「转换效果差」长期被归因于设备素质。**这是错的。**

**【实测】** 真正的根因是**页面尺寸错配导致的二次缩放**：

```
按 A4（210mm 宽）出页 → 投到 157.1mm 宽的屏幕
→ 设备将整页缩放至 74.8% 以适配
→ 设定的 11pt 实际只显示为 8.2pt
→ 且字形经重采样，无法对齐像素网格，hinting 失效，边缘发虚
```

用户对此**毫无察觉**，只会觉得「这块屏不够清晰」。

**【实测】** 消除缩放后，227 ppi 的墨水屏可呈现干净锐利的文字。
**清晰度的首要瓶颈是有无重采样，而非像素密度。**

## 2. 已验证的技术地基

以下事实构成产品的立足点。

### 2.1 设备物理参数

| 机型 | 分辨率 | 像素密度 | 显示区物理尺寸 | 依据 |
|---|---|---|---|---|
| QUADERNO A5 (FMVDP51) | 1404 × 1872 | 227.18 ppi | **156.97 × 209.30 mm** | **【实测】** 钢尺量 100mm 基准线正好 100mm |
| QUADERNO A4 (FMVDP41) | 1650 × 2200 | 206.77 ppi | **202.69 × 270.26 mm** | **【推算】** 未实测 |

推导法：`ppi = √(W²+H²) ÷ 对角线英寸` → `物理尺寸 = 像素 ÷ ppi × 25.4`
自验证：A5 反推得 227.18 ppi，与官方标称 227 ppi 吻合（误差 0.08%）。

### 2.2 设备显示行为

**【实测】** QUADERNO A5 以精确 1:1 显示 PDF——无缩放、无裁切、四角完整。
因此：**页面按显示区物理尺寸出图时，PDF 中的 10pt 即屏幕上真实的物理 10pt。**

**【实测】** 设备阅读器**支持 PDF 大纲（书签）并可跳转**，导航无需额外开发。

### 2.3 投递协议

**【实测】** 由逆向 `/Library/PDF Services/Print to QUADERNO.workflow` 获得：

```
open -gj -na "/Applications/QUADERNO PC App.app" --args --print <pdf路径>
```

关键行为：
- **【实测】** `-n` 不可省——macOS 不向已运行实例传递 `--args`
- **【实测】** `-g -j` 使其后台隐藏执行，不抢占焦点
- **【实测】** 客户端上传后会 **`unlink` 源文件**
- **【实测】** 客户端**仅在失败时写日志**，成功时静默无输出
- **【实测】** 6.5 MB / 348 页的 PDF 可正常投递；上限未知

## 3. 产品定义

### 3.1 一句话定义

> **让电子墨水设备以其原生物理尺寸呈现内容的工具链，及其背后的测定方法。**

### 3.2 三个层次

| 层 | 内容 | 价值范围 |
|---|---|---|
| **L1 投递管道** | 剪贴板 → 排版 PDF → 设备 | 仅 QUADERNO 用户 |
| **L2 电子书转换** | EPUB/MOBI → 设备优化 PDF | 仅 QUADERNO 用户 |
| **L3 测定方法与排版知识** | 显示区尺寸测定法、墨水屏排版规范 | **所有电子墨水设备** |

**L3 的适用面最广，且是 L1/L2 之所以有效的原因。** 产品叙事应以 L3 为纲。

### 3.3 设计哲学

1. **零 GUI 干预** —— 数据流管道，而非模拟点击。已明确否决 AppleScript 点击、Automator 录屏等基于 UI 树的方案。
2. **诚实优于完整** —— 严格区分实测与推论。宁可标注「待验证」，不可含糊。
3. **失败必须可见** —— 底层客户端静默失败，产品必须补上反馈。
4. **可读性即信任** —— 工具读取剪贴板、调用系统 API，用户应能在运行前读完源码。

## 4. 用户与场景

### 4.1 主要用户

以电子墨水设备进行**深度阅读**、并以命令行为主要工作环境的使用者。
其核心诉求是**隔绝 GUI 带来的注意力消耗**。

### 4.2 核心场景

| # | 场景 | 频次 | 当前解决度 |
|---|---|---|---|
| S1 | 把 AI 对话产出的 Markdown 送去阅读 | 高频、每次量小 | ✅ 已实现 |
| S2 | 把一本 EPUB 转换后送去阅读 | 低频、每次量大 | ✅ 已实现 |
| S3 | 调整排版参数至个人舒适 | 一次性 | ⚠️ 仅命令行 |
| S4 | 测定自己设备的物理参数 | 一次性 | ✅ 校准页已备 |

二者已拆分为独立工具（`deliver.sh` / `book.sh`），共享排版配置。

## 6. GUI 与预览的设计约束

**【推论】** 预览需要回答的问题分两类：

| 决策类型 | 等比缩放预览是否足够 |
|---|---|
| 行长、边距、页面留白、分章、图片位置 | **足够**——均为相对量 |
| 字号是否舒适 | **不足够**——需物理尺寸 |

但即便做到物理尺寸精确，**LCD 上的观感仍不等于墨水屏**：背光与反射、对比度、
灰阶、环境光均不同。**一个物理精确但显示在明亮 LCD 上的预览，会使人高估小字的可读性。**

### 设计决定

1. **默认等比预览 + 数字读数**（`32 字/行 · 12pt · 版心 137.1mm · 348 页`）。
   数字与缩放无关，不会误导。
2. **可选「实际尺寸」模式**：通过一次性尺子校准显示器获得其真实 PPI
   （复用本项目的校准方法，只是换一块屏）。须标注「字号舒适度以设备为准」。
3. **提供「发送样章到设备」入口。** 投递仅需约 2 秒。
   **与其做一个永远不够真的预览，不如让真设备成为预览器**——
   这是本管道相对其他方案的独特优势。

## 7. 质量不变量

以下条件在任何改动后都必须成立。**建议以 `test.sh` 固化为断言。**

| # | 不变量 | 由何种事故得出 |
|---|---|---|
| I1 | 输出 PDF **所有页**尺寸统一，且等于目标设备显示区 | 曾出现「正文正确、目录页与标题页为 us-letter」的混合尺寸 |
| I2 | 投递后**原始产物仍存在** | 曾因副本与产物同名，导致客户端删除原始文件，静默数据丢失 |
| I3 | 含 `@词`、`$变量` 的任意文本不致渲染失败 | pandoc 默认将 `@227dpi` 视为文献引用，`$PATH` 视为数学公式 |
| I4 | 含内部锚点的 EPUB 可正常渲染 | 手工尾注锚点在 typst 侧无对应 label，导致整本书渲染中止 |
| I5 | 在**空 locale + 无 Homebrew 的 PATH** 下仍可运行 | 快捷指令提供的即是此种最小环境 |
| I6 | 图片被约束在版心内 | — |
| I7 | PDF 大纲与目录页存在 | — |
| I8 | 失败时退出码符合约定（1/2/4/10） | — |

> **教训**：I1 与 I2 均**无法在合成测试样本上暴露**——前者需启用目录，后者需真实投递。
> 测试样本必须包含真实世界的复杂度。

## 8. 非目标

明确排除，避免反复讨论：

| 非目标 | 原因 |
|---|---|
| **上架 Mac App Store（带投递功能）** | **【实测】** 两条硬阻碍：① MAS 强制沙盒，沙盒应用无权以自定义参数启动第三方应用，而这正是投递协议的命脉；② pandoc 为 GPL-3.0，与 App Store 分发条款历来冲突。这两条与商标无关，已使该路径独立失效 |
| **以「Quaderno 助手」等含其商标的名称命名/上架** | 见下方 §8.1。商标风险几乎全部来自命名，而非功能；且功能不需要该品牌 |
| `curl \| sh` 一键安装 | 工具读取剪贴板并调用系统 API，用户应能先读源码。可读性即信任机制 |
| 模拟点击 / UI 自动化 | 基于像素与 UI 树的方案极脆弱，与设计哲学冲突 |
| 自动创建快捷指令并绑定热键 | **【实测】** Apple 不允许，快捷指令仅可授予只读点击权限。此步骤必须手动 |
| 破解 DRM | 不在支持范围 |
| 支持非 QUADERNO 设备的**投递** | 投递协议为该客户端特有。但 **L3 的测定方法通用** |

### 8.1 命名、商标与分发合规

> 非法律意见。任何商用/上架前须经 IP 律师复核，并查阅 QUADERNO PC App 的
> EULA（是否含禁止逆向工程 / 禁止自动化条款——那是合同层面的约束）。

**核心判断：本产品的功能不依赖 Quaderno 的任何知识产权。** 它需要的只是一个
屏幕物理尺寸（156.97 × 209.30 mm），而尺寸是**事实**，不是 IP。逆向得到的
`open --print` 协议是对**用户自己已安装**的客户端的本地调用，未复制其代码、
未打包其二进制、未破解 DRM。因此实质 IP 风险几乎只剩一处：**命名**。

| IP 类别 | 风险 | 结论 |
|---|---|---|
| 商标 | 把 app 命名为「Quaderno 助手」等，用其注册商标作产品身份锚点，暗示官方关联；亦触发 App Store 审核指南 5.2 | **避免**。功能不需要该品牌 |
| 版权 / 逆向 | 仅调用已安装客户端、未复制代码、未破解 DRM，通常落在互操作范围内 | 风险较低，但须查 EULA 的反逆向条款 |
| 专利 | 格式转换 + 打印路由不太可能撞有效专利 | 基本不相关 |

**据此确立的命名与分发规则：**
1. **中性命名**（如「电子书转换 / e-ink 排版工具」），不以其商标为产品名。
2. **事实性兼容声明**：可写「兼容 QUADERNO A5 及同尺寸墨水屏」（名义性合理
   使用），但不得暗示官方/授权/背书，不得使用其 logo。
3. **保留免责声明**（README 已有）：
   *Not affiliated with or endorsed by Fujitsu. QUADERNO is their trademark.*
4. **分发走 App Store 之外**：公证 DMG / Homebrew / GitHub Release —— 不受
   沙盒、GPL、Apple 5.2 名称审查限制。
5. **触达 Quaderno 用户靠 SEO**（官网技术文章能被「quaderno epub pdf」搜到），
   而非把品牌名塞进 app 标题——前者合法且更有效。

## 9. 未验证的假设与风险

| # | 假设 | 风险 | 验证方式 |
|---|---|---|---|
| A1 | A4 机型显示区为 202.69 × 270.26 mm（按官方 13.3″ 推算） | A4 用户拿到错误版面 | 需一位 A4 用户跑校准页 |
| A1b | **竞争假设**：A4 与 A5 像素密度相同（227.18 ppi），则显示区为 184.48 × 245.97 mm | 两假设页宽差 **18.2 mm（9%）**，取错则版面全盘偏移 | 同上，一次实测即可定夺 |
| A2 | 客户端「标题/作者」列读取 PDF metadata | F13 方案可能落空 | 写入元数据后观察客户端 |
| A3 | 浅于约 40% 的灰在墨水屏上不可辨 | 影响辅助文字用色 | 灰阶阶梯页已投递，待读数 |
| A4 | 1:1 显示使手写更跟手 | 若成立是重要卖点 | 需盲测或高速摄影 |
| A5 | mobi/azw 经 calibre 中转可行 | 代码已写但**从未运行** | 需 calibre 与测试文件 |
| A6 | 上传体积无实用上限 | 大书可能失败 | 递增测试 |

**关于 A1 与 A1b 的现有证据**（均未实测，仅供参考）：

| | A1（官方 13.3″） | A1b（同 227 ppi） |
|---|---|---|
| 隐含对角线 | 13.3″ ✓ 与官方一致 | **12.10″** ✗ 与官方 13.3″ 矛盾 |
| 反推左右边框 | 10.1 mm | **19.2 mm** |
| 反推上下边框合计 | 30.8 mm | **55.1 mm** |
| 与 A5 实测边框（8.1 / 33.2 mm）比较 | 比例相近 | 侧边框近 2 cm，对该类设备不合常理 |

现有证据偏向 A1，但**两者均未实测**，且 9% 的差异足以毁掉版面。
在拿到 A4 实测数据前，代码中的 A4 参数应显著标注为未验证。

**【已推翻的假设，记录以备参考】**
初稿曾假设「宋体因横细竖粗，在 227 ppi 下会发虚」。实测推翻：
宋体细横笔约 1/12 em，@10pt 约 2.6 像素，渲染扎实；
真正失效的是 Computer Modern 一类约 1/30 em 的发丝衬线（约 1.05 像素）。
**该次错误同时伴随一处证据误读**——将早期 A/B 的「两者皆可」读作「其一胜出」以支撑假设。
详见 `docs/typography-for-eink.md`。

| 术语 | 含义 |
|---|---|
