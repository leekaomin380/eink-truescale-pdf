# 扫描书上墨水屏：可读性的几何模型

> 本项目既有的转换路径处理的是**流式文档**（EPUB / HTML / FB2 / Markdown）——
> 版面由我们生成，字号可以随便定。
> 扫描书是另一类问题：版面在纸上已经固定，我们**只能整体缩放或切分**，不能改行长。
> 这类源进小屏时"字太小"的根因是纯几何的，与分辨率无关。
>
> 本文给出可读性放大倍率的支配不等式、一条反直觉的推论，以及实测数据。
>
> 三类标注：
> **【推导】** 由几何关系导出，无需实测
> **【实测】** 本项目实际测量所得，附条件
> **【方法】** 可复用的操作步骤

---

## 关键结论（TL;DR）

以一本 A4 扫描书进 QUADERNO A5 为例：

| 方案 | 正文放大倍率 | 说明 |
|---|---|---|
| 整页直塞（默认行为） | **0.734×** | 字被压到印刷尺寸的 73%，这就是"看不清"的全部原因 |
| **仅裁掉页边白** | **0.734×** | **零增益**。见第三节，这是最容易犯的错 |
| 裁切 + 纵向切分（竖持） | **1.236×** | 比纸书还大 24% |
| 裁切 + 纵向切分（横持） | **1.648×** | 页数×3 |
| 换 13.3″ 设备 | **0.948×** | 近似 1:1，**零处理** |

最后一行值得单独标注：**换设备是唯一能取消问题的方案**。任何工具方案都应当拿它做基准比价——
如果一台 13.3″ 设备的价格低于你对若干天工程量的估值，后面的技术分析就没有必要做。

---

## 一、支配不等式

【推导】屏上字的物理大小 = 原印刷字号 × M。而 M 有硬上限：

```
M ≤ 屏幕可用宽度 / 必须完整放下的最小横向单元宽度
```

分母是**不重排时不可分割的横向单元**。对扫描件而言就是**一整行**，因为行内没有可利用的断点
（位图无法在不做识别的前提下重排）。

于是全部解法只有三条，各自攻击不等式的一个量：

| 攻击对象 | 手段 | 代价 |
|---|---|---|
| 分子（屏宽） | 换更大的屏 / 旋转设备 | 硬件成本 / 横持 |
| 分母（行宽） | 重排——必须先识别，把"行"这个原子打碎 | OCR 工程量与错误率 |
| 前提（原印刷字号） | 换一个文字版的书源 | 未必存在 |

**裁切与切分都不在这张表里**——它们不改变 M 的上限，只是让实际 M 逼近上限。

## 二、实测参数（本项目样本）

【实测】样本：某 A4 幅面扫描教科书，复印机直出。

| 项 | 值 |
|---|---|
| 页面尺寸（已应用 `/Rotate`） | 581.04 × 807.84 pt = **204.9 × 285.0 mm** |
| 每页内容 | 单张 4488 × 3228 RGB JPEG，**400 dpi** |
| 文本层 | **无**（`pdftotext` 每页返回 1 字节） |
| 正文栏宽 | **约 127 mm**，外侧留白约 68 mm，奇偶页镜像 |
| QUADERNO A5 显示区 | **156.97 × 209.30 mm**（见 `devices.json`，已钢尺实测） |

由此：

```
整页直塞    209.30 / 285.0 = 0.734
切分后竖持  156.97 / 127.0 = 1.236
切分后横持  209.30 / 127.0 = 1.648
13.3″ 设备  270.26 / 285.0 = 0.948
```

**400 dpi 远超 227 ppi 面板能呈现的上限——信息量从来不是瓶颈，瓶颈是视角。**
这一点决定了任何"提高清晰度"的努力都不会改善可读性。

## 三、由此得出一条不直观的结论

> **当源页是高度受限时，裁掉页边白对字号零增益。**

【推导】源页宽高比 204.9/285.0 = 0.719，小于屏幕的 0.750，因此适配时**高度先触边**。

把宽度从 204.9 mm 裁到正文栏的 127 mm，页面变成 127 × 285 mm、宽高比 0.446，
**仍然高度受限**，缩放系数一样是 209.30/285.0 = 0.734。字一点没变大，
只是屏幕左右多出 37% 的空白，主观上更差。

**要放大必须切分高度。** 裁宽度只有在与纵向切分组合时才有意义：
先裁掉外侧栏得到 127 mm 的正文栏，再把 285 mm 的高度切成两段，此时约束才从高度转到宽度，
M 才能升到 156.97/127.0 = 1.236。

判据很简单：

```
源宽高比 < 屏宽高比  →  高度受限  →  裁宽无用，必须切高
源宽高比 > 屏宽高比  →  宽度受限  →  裁宽有效
```

## 四、切分参数【推导】

一旦进入宽度受限，M 就被钉死在 `屏宽 / 内容宽`，**再多切几刀也不会更大**。
所以切分的刀数只决定"每屏用掉多少垂直空间"，不决定字号。

竖持，内容宽 127 mm：

```
M = 156.97 / 127.0 = 1.236
每屏可容内容高 = 209.30 / 1.236 = 169.3 mm
页内容高约 272 mm → 2 屏/页，重叠 66 mm
```

取**重叠**而非留缝：同样的字号下，重叠让跨切口的段落在两屏中都完整出现，
消除"半句被切在屏幕边缘"的问题，代价只是少量重复阅读。

横持，内容宽 127 mm：

```
M = 209.30 / 127.0 = 1.648
每屏内容高 = 95.2 mm → 3 屏/页
```

## 五、【方法】PDF 页码 ≠ 印刷页码

扫描书的 PDF 页序包含封面、版权页、前言等前置部分，与书上印的页码存在固定偏移。
本项目样本的偏移是 **32**（PDF 第 177 页 = 印刷第 145 页）。

按印刷页码去 PDF 里抽章节，会抽错——本项目样本上，按印刷页码抽"第 6 章"
实际拿到的是第 5 章的末尾。

**可靠的定位法：用章首页的几何特征做扫描，而不是翻页找。**

多数教科书的章首页有固定的视觉签名（大色块标题条、右上角图版）。以本项目样本为例，
章首页右上角有深色图版，对候选区间逐页计算该象限平均灰度，孤峰即章首页：

```
PDF p208 (印刷176)  219.8
PDF p209 (印刷177)  242.5
...
PDF p213 (印刷181)  123.1   ← 孤峰，第 7 章章首页
PDF p214 (印刷182)  242.5
```

低分辨率渲染（25 dpi 即可）足够，全程数秒。确认两个相邻章的章首页后，
章的 PDF 页范围与偏移量同时确定。

## 六、【方法】坐标映射必须先做可视校验

若借助外部 OCR / 版面分析工具（其输出坐标基于它自己的渲染分辨率），
把坐标映射回原始 PDF 时，**在批量处理前必须先验证映射正确**。

本项目样本：OCR 工具按 144 dpi 渲染，页面 581.04 × 807.84 pt → 光栅 1162 × 1616 px，
映射到 400 dpi 的系数为 `400/144 = 2.777778`。交叉验证：

```
1162.08 × 2.777778 = 3228.0    与 PDF 内嵌图的 4488 × 3228 一致 ✓
```

有了等式还不够——**必须再挑几张图裁出来与整页渲染并排肉眼比对**。
`/Rotate` 的处理、y 轴方向、原点位置任一环出错，等式都可能照样成立而图裁错位置。
这一步花几分钟，跳过它则后面全部白做。

## 七、与本项目现有能力的关系

扫描书路径的产物是 EPUB，随后走既有的 `book.sh` → Typst 管线出设备 PDF。
也就是说：

- **第一~四节的几何分析，在拿到文字版之后就全部失效**——因为重排后行宽由我们定，
  M 的上限消失，直接用 `--size` 设字号即可。
- 几何模型的用途是**决策**：判断值不值得为一本书做 OCR，还是直接切分位图更划算，
  又或者干脆换设备。

不建议把 OCR 内嵌进 app：`docs/PRODUCT.md` 第 2 节承诺"处理在本地、不上传用户文档"，
而可用的中文文档解析模型在 macOS arm64 上部署困难，走云 API 则直接破坏该承诺。
合理形态是仓库内的独立 CLI——用户自选 OCR 引擎与运行环境，工具只消费其结构化输出。
