## 1. 背景（Why）

当前 app 有两种输入：电子书文件（EPUB 等）和粘贴 Markdown 文本。用户希望增加第三种：
**直接粘贴微信公众号文章链接**，自动抓取正文并渲染成 1:1 PDF，然后发送到 Quaderno。

好消息是：这个功能在用户的另一个项目 ReadIsland（`Print-to-p6`）中**已经完整实现并
经过真机实测**，包括 macOS 原生版本。本任务的核心是**移植 + 简化**，不是从零设计。

关键简化：ReadIsland 是「端侧抽取 → 上传服务器 → 服务器投递到墨水屏」的架构，
本项目**完全本地**，没有服务器、没有上传 token、没有备份轨道。抽取失败就是失败，
直接告诉用户，不需要回退到任何远程服务。

### 3.1 ⚠️ 唯一的架构差异（最容易搞错的地方）

参考项目是 **Share Extension**：HTML 由微信 App 通过分享菜单递进来，它**本来就不需要
自己联网**，所以 `WeChatExtractor` 用 `WKContentRuleList` **全量 block 一切网络请求**
（隐私考虑 —— 不让腾讯 CDN 知道用户在读哪篇文章，顺带解析快 6 倍）。

**我们的场景不同**：用户粘贴的是 URL，我们**必须自己抓 HTML**。所以：

```
URLSession 抓 HTML          ← 必须联网（这是我们获取内容的唯一途径）
   ↓
WKWebView 加载 HTML 跑 JS   ← 【仍然全量 block】保持参考实现原样，见下
   ↓
URLSession 下载图片          ← 必须联网（ImageInliner 自己用 URLSession，不受 WebView 规则影响）
```

**关键点**：`WKContentRuleList` 只作用于**那个 WKWebView 实例内部的资源加载**，
对 `URLSession` 毫无影响。所以「WebView 里全量 block」与「我们用 URLSession 抓 HTML
和图片」**不冲突，可以共存**，且必须保持 block —— 理由（参考项目实测）：
- WebView 加载 HTML 时会真的去拉里面的绝对 URL（`baseURL:nil` 只挡相对地址）
- 不挡的话：白等腾讯 CDN（实测 1343ms vs 阻断后 225ms，**快 6 倍**）
- 图片我们要的是 `data-src` 里的 URL 字符串，由 ImageInliner 主动去取，**不需要
  WebView 帮我们加载**

所以：**照抄 `WeChatExtractor.swift`，不要因为"我们需要联网"就把 block 规则删掉。**

### 3.2 参考实现里已经踩过的坑（照抄即可规避，改动前务必想清楚）

这些都写在参考项目的注释里，摘录最关键的：

1. **微信图片是懒加载**：真实 URL 在 `data-src`，`src` 常为空。实测一篇文章 13 个
   `<img>` 里只有 4 个有非空 `src`、5 个有 `data-src`，其余是裸标签占位。
   只读 `src` 会漏掉大部分图。（抽取器已处理）
2. **微信 CDN 无防盗链**：裸请求（无 UA、无 Referer）即 200，不需要伪造请求头。
3. **图片处理"处理后比原图大就用原图"**：灰度+JPEG 在大 PNG 上大赚（182KB→80KB），
   但在已压好的小 JPEG 上是净亏（31KB→47KB，小 PNG 1.2KB→6.3KB 大 5 倍）。
   实际比一比，别按规则猜。
4. **绝不放大图片**：`sips -Z` 那种"缩放到框内"会把 197×197 放大到 1440×1440
   （7 倍），4 张图 247KB 反而涨到 378KB。只在超过 `maxEdge`（2400）时缩。
5. **JPEG 质量用 0.5 不是 0.75**：q75 实测只省 1%（微信给的本就是压好的 JPEG），
   q50 省 37%。墨水屏只有 16 级灰度，q50 与 q75 的差别在目标设备上**物理不存在**。
6. **`WeChatExtractor` 必须自持（`selfRetain`）**：类内到处是 `[weak self]`，
   若调用方写成临时对象，ARC 会立刻回收 → **回调永不触发且完全静默**。
7. **必须实现 `webViewWebContentProcessDidTerminate`**：WebContent 是独立 XPC 进程，
   可能被系统单独杀掉，不处理则回调永不触发。
8. **抽取器 JS 里 SCRIPT/STYLE/NOSCRIPT 必须跳过**：微信排版工具（135editor/秀米）
   常在正文容器内嵌 `<style>`，不跳过会把 CSS 源码当正文推进 markdown。

## 4. 具体步骤

### Part A — 移植抽取核心

1. 新建目录 `gui/mac/wechat/`，放入从参考项目复制的文件：
   - `wechat_extractor.js`（原样）
   - `WeChatExtractor.swift`（原样，仅在必要时调整 `import`/命名冲突）
   - `ImageInliner.swift`（原样）
   - `LocalExtraction.swift`（**简化版**，见下）
2. `LocalExtraction.swift` 的简化：
   - 保留：`extractorJS` 载入、`run()` 的成功判定（`ok && outcome=="OK" &&
     markdown.count >= minBodyChars`）、`Outcome` 结构
   - 删除：`stripScripts()`（那是给"上传原始 HTML 到服务端"的备份轨用的，我们没有）
   - `Outcome` 里的 `elapsedMs` 建议保留（调试有用），`reason` 必须保留（要给用户看）
3. **JS 文件的打包问题（关键）**：参考项目用 `Bundle.main.url(forResource:)` 从
   app bundle 读 JS。我们的 `build-app.sh` 目前不拷贝任何资源文件到
   `Contents/Resources/`（除了图标）。两个方案任选，在回报里说明选了哪个：
   - **方案一**：`build-app.sh` 增加一行，把 `wechat_extractor.js` 拷进
     `$APP_DIR/Contents/Resources/`，Swift 侧用 `Bundle.main.url` 读取
   - **方案二**：把 JS 作为 Swift 字符串常量内嵌（`let extractorJS = #"""..."""#`），
     不依赖 bundle 资源
   方案一更接近参考实现且便于日后更新 JS；方案二构建更简单、不会因忘记拷贝而
   静默失效。**倾向方案一**，但要在 `LocalExtraction` 里对"JS 没读到"给出明确错误
   （参考实现的 `js_not_bundled`），不能静默降级。

### Part B — 抓取 HTML

4. 复制参考项目 `SenderService.swift` 的 `fetchWechatHTML` 方法（约 264-290 行）。
   要点：`URLSession.dataTask`、15 秒超时、带 iPhone Safari 的 User-Agent、
   `String(data:encoding:.utf8)` 失败时回退 `.ascii`。
5. URL 校验：只接受 host 为 `mp.weixin.qq.com` 的链接。其它链接给出明确提示
   （"目前只支持微信公众号链接"），不要尝试通用网页抽取 —— 那是另一个量级的问题。

### Part C — 接入 GUI

6. `ContentView.swift` 的 `InputMode` 枚举增加 `case wechat = "公众号链接"`。
7. 该模式的界面：一个单行 URL 输入框 + 「解析并预览」按钮。解析过程中显示进度状态
   （抓取中 → 抽取中 → 下载图片中 → 渲染中），因为这条链路有网络，可能要几秒。
8. `ConversionViewModel` 增加 `func convertWechat()`，流程：
   ```
   校验 URL → fetchWechatHTML → LocalExtraction.run（主线程）
   → ImageInliner.inline → 得到最终 markdown
   → 【复用现有渲染路径】写入临时 .md 文件 → book.sh --plain → PDF
   ```
   **注意第三步**：现有 `convertText()` 已经完整实现了「markdown → 临时 .md →
   `book.sh --plain` → PDF → 更新预览/页数/metrics」。请**提取公共部分复用**，
   不要把那三十行复制一遍 —— 两份渲染逻辑早晚漂移（这是本项目 `config.sh` 存在的
   同一个理由）。建议把 `convertText()` 里从"写 .md 文件"开始的部分抽成一个私有
   方法，如 `renderMarkdown(_ markdown: String, title: String)`，两处共用。
9. 标题处理：抽取器返回的 `title`/`author`/`date`/`site` 应当利用起来。
   最简做法：把 `title` 传给现有的 frontmatter 注入逻辑（`convertText()` 里已有），
   这样 PDF 元数据和投递文件名都会带上文章标题。`author` 可选择性加入 frontmatter。
10. 失败提示要具体，按抽取器返回的 `outcome` 分别处理：
    - `RISK_GRAY` → "微信要求验证，请稍后再试或在微信中打开一次该文章"
    - `CONTENT_GONE` → "该文章已被删除或无法查看"
    - `STRUCT_MISSING` / `EXTRACT_EMPTY` → "未能识别正文结构（可能不是文章页）"
    - 网络错误 → 显示具体错误
11. 「另存 PDF」「发送到 Quaderno」在该模式下同样可用，沿用现有 DIRTY/复用逻辑。
