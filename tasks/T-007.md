## 2. 背景（Why）

项目最初就是一条 shell 命令 + 一个 macOS 快捷指令绑定的全局热键（⌃⌥⌘P）：
读剪贴板 → 渲染成 1:1 PDF → 投递到 QUADERNO。后来长出了 GUI app。

**现状是：作者已经不再使用快捷指令那条路径，只用 app。** 因此产品形态应当收敛 ——
热键功能由 app 自己提供，不再依赖用户手动配置快捷指令。

这样做的收益：
- 省掉 README 里最长、最劝退的一节（手动创建快捷指令的七个步骤 + 四个下拉框设置）
- 热键触发时可以使用**用户在界面上调好的排版参数**，而快捷指令那条路只能用
  `config.sh` 里的默认值 —— 这是集成的核心价值
- 一个 app 覆盖全部功能

**技术可行性已由委托方实测确认**（不必重新验证，但要按这个结论实现）：
Carbon 的 `RegisterEventHotKey` 可以在**完全没有辅助功能权限**的情况下注册全局热键。
实测输出：
```
辅助功能权限(AXIsProcessTrusted): false
✅ RegisterEventHotKey 成功注册 ⌃⌥⌘P（无需辅助功能权限）
```
**不要改用 `NSEvent.addGlobalMonitorForEvents`** —— 那个需要辅助功能权限（因为它能监听
所有按键），会平白给用户增加一道授权门槛。

### 设计决策（已定，按此实现）

**热键触发时走 app 内部的管道，不要调用 `deliver.sh`。** 理由：
1. 不必再往 bundle 里塞一个脚本
2. **可以使用界面上当前的参数**（用户调过的字体/字号/边距/行距/目标设备），
   而不是 `config.sh` 的静态默认值 —— 这正是集成到 app 的意义所在
3. 逻辑单点，避免两套渲染路径漂移

**但注意：不能直接复用 `renderMarkdown` + `deliverToDevice`。** 那两个方法会改写主窗口的
状态（`currentPdfURL`、`totalPages`、`renderMetrics`、预览图、状态栏文字）。热键的价值在于
**不打断用户当前正在做的事** —— 如果用户正在 app 里预览一本 epub，按热键投递一段剪贴板文字
却把预览换成了那段文字，是错的。

因此需要一条**独立于主窗口状态的**剪贴板投递流程。它可以复用底层的 shell 调用与投递逻辑，
但不得改写上述 `@Published` 状态。具体如何组织由你决定，在报告中说明。

## 4. 目标（What）

1. app 常驻菜单栏；关闭主窗口后进程存活，热键继续有效。
2. 注册全局热键（默认 ⌃⌥⌘P），按下时：读剪贴板 → 用当前界面参数渲染 → 投递到 QUADERNO
   → 发系统通知报告结果。**全程不打断用户，不抢占焦点，不改变主窗口状态。**
3. 菜单栏菜单至少提供：打开主窗口、启用/停用热键、退出。
4. 失败要可见（沿用项目一贯原则：静默失败是不可接受的）：
   - 剪贴板为空 → 通知
   - 渲染失败 → 通知（带原因摘要）
   - **热键被其它 app 占用 → 必须明确告知用户**（见下）

### ⚠️ 必须处理的冲突场景

作者此前已在 macOS 快捷指令里把 ⌃⌥⌘P 绑给了 `deliver.sh`。若那个绑定仍然存在，
app 注册同一组合键时 `RegisterEventHotKey` 会失败（`eventHotKeyExistsErr`）。

**这种情况绝不能静默失败**（用户会以为功能坏了却毫无线索）。必须：
- 在菜单栏菜单或主窗口中明确显示热键当前状态（已注册 / 注册失败及原因）
- 失败时给出可操作的提示，例如「⌃⌥⌘P 已被其它程序占用，请在系统设置或快捷指令中
  解除绑定后重试」
